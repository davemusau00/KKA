# UI surfaces and flow integration audit

Audit date: 2026-09-07. Scope: `apps/web/src`, its shared state/API adapters, and corresponding API controllers/services. This is a source audit, not a new browser acceptance run or certification of backend completeness. No provider messages, payments, backups or production mutations were executed.

## Coverage and interpretation

The reproducible [inventory](UI_SURFACE_INVENTORY.json), generated by `node scripts/audit-ui-surfaces.mjs`, contains:

- **63 component files**, of which **62** are reachable through relative runtime imports from `App.tsx`.
- **1,054 native control declarations** (`button`, `input`, `select`, `textarea`, `form`, `a`), plus **63 other interaction candidates**. These are source nodes, not distinct rendered actions or defect counts.
- **112 AppContext callbacks**, only **12** of which contain direct API-adapter calls. Presentation helpers and callbacks that delegate elsewhere are included; this is not an implementation percentage.
- Control attributes/handlers, context bindings, API calls, source lines and the audited Git revision. Import reachability does not establish that a permission, tab or data-dependent condition exposes a component to every user.

The findings below come from tracing representative actions and their supporting code. Every declaration is inventoried; not every runtime permutation has been manually exercised. Backend endpoint existence is recorded separately from a complete, authorized, persistent user workflow.

Status terms: **integrated slice** means a specific server-backed path with existing acceptance evidence; **unintegrated** means the UI does not consume an available API correctly; **prototype-only** means local/synthetic behavior; **unavailable** means there is no operational UI path or the control is explicitly disabled. All agreed launch phases remain required.

## Highest-priority findings

### U01 — Integration tests turn failures into success (P0, prototype-only)

`IntegrationsWorkspace` catches a failed connection test and, after 800 ms, reports successful Google synchronization, Judiciary polling, Meta verification or Daraja authentication. WhatsApp and M-Pesa buttons manufacture delivery/payment notifications and random transaction references. There is no demo-mode condition around these handlers. Saving credentials only updates browser state.

Evidence: [integration handlers](../apps/web/src/components/integrations/IntegrationsWorkspace.tsx#L59), [configuration mutation](../apps/web/src/context/AppContext.tsx#L3817). The UI passes provider labels such as `google` to an endpoint that expects a stored connection ID. It expects `success/message/latencyMs`; the service returns `status/detail` and explicitly marks unsupported adapters `NOT_IMPLEMENTED`: [API adapter](../apps/web/src/lib/api/integrations.api.ts#L15), [backend test](../apps/api/src/modules/integrations/integrations.service.ts#L105).

Acceptance: an unconfigured provider or failed HTTP request must display unavailable/failed; saving must persist encrypted server configuration; real test results must reference the saved connection; manual communication/payment evidence must never imply a provider transaction.

### U02 — Backup/restore controls fabricate operational evidence (P0, prototype-only)

Create Snapshot generates a random size/checksum and a `completed` record without a backup job. Restore only logs/notifies and returns `true`; its UI claims a sandbox restore. The diagnostic download is a real JSON download, but its contents include local counts/configuration and a hard-coded version, not a verified infrastructure diagnostic.

Evidence: [System Operations handlers](../apps/web/src/components/admin/tabs/SystemOperationsTab.tsx#L55), [snapshot/restore implementation](../apps/web/src/context/AppContext.tsx#L3430). Shell backup runbooks are not connected to this UI.

Acceptance: expose actual job/file/checksum/restore-test evidence from an authorized backend; failed or absent jobs cannot be completed snapshots. No release evidence may rely on these current buttons.

### U03 — Finance and client-money actions are local ledger imitations (P0, prototype-only)

Fee notes, requisitions, deposits, approvals, disbursements, trust applications and time billing mutate context arrays. Displayed trust balances subtract approved expenses even before disbursement and are not derived from journal postings. These actions never call the existing finance routes.

Evidence: [FinanceWorkspace state/calculations](../apps/web/src/components/finance/FinanceWorkspace.tsx#L31), [expense/receipt/fee-note mutations](../apps/web/src/context/AppContext.tsx#L3497), [available journal/receipt/ledger API](../apps/api/src/modules/finance/finance.controller.ts#L1).

Acceptance: persist complete postings/allocations, prove reversals, duplicate protection and reconciliation, then derive balances and reports from authorized ledgers. The existing finance screen is not an accepted finance workflow.

### U04 — Matter documents and central approvals bypass the real document engine (P0, unintegrated)

Top-level Documents uses `DocumentStudio`, but matter document previews and the centralized approvals screen consume the old context document collection. Local signing manufactures an `LSK-SIG-*` string, sets `signed` and announces “Digitally Signed.” The old preview initializes a random Judiciary filing reference. These are separate from stored immutable PDF application and approval records.

Evidence: [main document route](../apps/web/src/App.tsx#L13), [matter preview mount](../apps/web/src/components/matters/MatterDetailWorkspace.tsx#L1100), [old preview](../apps/web/src/components/common/DocumentPreviewModal.tsx#L17), [local signature](../apps/web/src/context/AppContext.tsx#L3055), [central approvals bindings](../apps/web/src/components/approvals/ApprovalsWorkspace.tsx#L28).

Acceptance: one document/version identity and approval pipeline across matter, top-level Documents and approvals; remove fabricated signing/filing evidence; preserve original bytes and immutable legal status history. Certificate signing remains a separate missing workflow.

### U05 — Empty PI stages invent completed case facts (P0, prototype-only)

Several stage components fall back to populated example evidence, medical/legal assessments, awards, recovery and settlement state when a matter has no saved stage data. Clearing global seeds at startup does not prevent these per-component fallbacks. For example, the judgment initializer marks recovery triggered. Save controls often show “Synced” after only a context update.

Evidence: [judgment initializer/save](../apps/web/src/components/matters/workflows/JudgmentAwardWorkspace.tsx#L23), [recovery initializer/save](../apps/web/src/components/matters/workflows/RecoveryExecutionWorkspace.tsx#L24), [incident save](../apps/web/src/components/matters/workflows/IncidentEvidenceWorkspace.tsx#L126), [PI API](../apps/api/src/modules/personal-injury/personal-injury.controller.ts#L8).

Acceptance: a new matter has empty evidence, no invented court order/payment/medical fact, and no completed stage. Every stage save must persist through its authorized backend and survive another user's session.

### U06 — Staff invitation, suspension and assignment are not account administration (P0, unintegrated)

Staff Directory creates a local `usr-*` record and calls it added; toggling activity/branch or changing roles only changes context. No invitation is issued and a “suspended” account is not suspended on the server. Staff is cleared at production startup and not fetched by the main hydration routine.

Evidence: [staff bindings](../apps/web/src/components/admin/tabs/StaffDirectoryTab.tsx#L35), [local user mutations](../apps/web/src/context/AppContext.tsx#L3282), [role mutations](../apps/web/src/context/AppContext.tsx#L3218), [users API controller](../apps/api/src/modules/users/users.controller.ts).

Acceptance: invite delivery/acceptance, server role assignment, branch membership, suspension and session revocation must be one audited workflow; verify access using a second authenticated session.

### U07 — Sync Center marks work synchronized without sending it (P0, prototype-only)

`triggerSync` waits, labels every mutation `synced`, then clears the queue without an HTTP operation. The shell still exposes the Offline PWA & Sync Center and its simulated connectivity controls despite offline synchronization being deferred.

Evidence: [sync callback](../apps/web/src/context/AppContext.tsx#L1182), [sync surface](../apps/web/src/components/common/OfflineSyncCenterModal.tsx#L12), [shell mounts/navigation](../apps/web/src/components/layout/AppShell.tsx#L40).

Acceptance: enforce online-required business changes. No simulated queue acknowledgment or local connectivity toggle may imply server persistence.

## Recommended implementation order

1. Eliminate U01–U07 false-success/legal/financial evidence paths and align production visibility. Preserve their required launch scope; hiding them does not complete them.
2. Fix session/domain loading and shared response contracts (U08/U10/U11/U16), then route all business state through server queries and stable URLs.
3. Complete identity/organization administration and scoped policies (U06/U17–U19/U21/U23/U25), including server authorization before exposing more API data.
4. Build intake → matter → legal work through the shared document/approval spine, replacing each local stage save with a complete vertical workflow.
5. Complete communication, finance, external access, firm operations and advanced launch phases with their own acceptance evidence.

## Evidence limits and maintenance

The earlier 35 passing checks cover foundation, organization-profile and document increments. They do not exercise these prototype flows or prove that every visible surface is integrated. This audit adds no runtime acceptance passes. Regenerate the inventory when source changes, then review findings before marking any fixed. Run cross-role, reload/second-user, failed-request, concurrency and mobile scenarios for each converted flow.
